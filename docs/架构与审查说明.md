# Hermes QQ Bridge：架构与审查说明

> 本文面向代码审查人、潜在贡献者与部署者，说明项目的全局目标、职责边界、数据流、当前实现状态和后续迭代方向。

## 一、审查结论先行

本项目不是一个新的 Agent 框架，也不是为了在 QQ bridge 中重写对话、记忆、工具调用与调度。

它采用的总体策略是：

```text
OneBot/NapCat 的 QQ 协议复杂性留在桥接边界
Hermes Agent 的通用 Agent 能力留给 Hermes 原生框架
群聊人格与行为判断留给独立 Hermes Profile
```

换言之：

```text
Bridge 解决“消息怎么安全、准确地进出 QQ”
Hermes 解决“模型如何会话、记忆、用工具、执行任务”
Profile 解决“这个群里该不该说、怎么说、怎样逐步学习”
```

这样可以避免在 bridge 中复制 Hermes 已经提供的能力，降低维护成本，也保证模型、工具、记忆、MCP、Cron 的升级路径始终跟随 Hermes 原生框架。

---

## 二、分层职责

### 1. QQ / OneBot / NapCat 层

职责：把 QQ 原始事件可靠传递到 bridge，并发送 OneBot 格式消息。

关键对象：

```text
群号
发送者 QQ
消息 ID
@ 段
回复关系
图片、文件、视频、语音等消息段
```

这一层不应决定模型是否理解了话题，也不应提供人格规则。

### 2. Bridge 层（本仓库）

职责：协议适配与安全边界。

目前参考实现位于：

```text
plugins/hermes_bridge.py
```

负责或演示：

- NoneBot2 / OneBot v11 事件入口；
- 群消息短时缓存与合并；
- 会话标识构造；
- 发送者、消息 ID、@、回复关系的基础保留；
- 图片、文件、闪照等附件的 URL / 本地路径规范化；
- 附件落盘路径安全；
- 调用 Hermes API；
- 只向 QQ 发送最终自然语言回复；
- 脱敏日志与内部错误隔离。

Bridge 不应负责：

```text
完整聊天历史管理
长期记忆
用户画像
搜索引擎封装
MCP 生命周期
模型工具调用循环
群聊人格
用“随机概率”替代模型语义判断
```

### 3. Hermes 原生 Agent 层

由 Hermes 负责：

```text
Profile 配置隔离
Gateway 生命周期
Agent loop
模型调用与多轮 tool calling
Session / state.db / routing
会话压缩与历史检索
Memory / Mem0
Toolsets 与 Tool Registry
MCP server 连接、发现、重连
Skills 的按需加载
Cron、watchdog、任务调度
Provider / fallback / credential routing
```

桥接项目应尽量通过 Hermes 配置和原生接口复用这些能力，而不是在 Python bridge 里复制它们。

### 4. QQ 群 Profile 层

独立 Profile 负责：

```text
人格（SOUL）
按群差异化语气
是否接话
是否需要搜索、查历史、读文件、看图
工具结果如何转成自然聊天回复
用户画像与群内关系摘要
渐进式披露的记忆读取
```

这里的核心原则是：

```text
代码保护协议与安全边界
模型判断普通群聊行为
```

不应使用固定关键词、随机丢消息或机械“十条回一条”去替代模型理解现场。

## 三、端到端数据流

```text
(1) QQ 群友发送消息
        ↓
(2) NapCat 产生 OneBot v11 Event
        ↓
(3) Bridge 接收事件
    - 识别群号、发送者、消息 ID、@、reply
    - 规范化附件位置
    - 做协议安全与短时合并
        ↓
(4) Hermes Gateway / Profile 接收群聊 turn
    - 载入当前群的 session
    - 载入核心 SOUL
    - 只在需要时读取群级资料、用户摘要、Skill
        ↓
(5) 模型决定
    A. 不值得参与 → `NO_REPLY`
    B. 当前上下文足够 → 生成自然回复
    C. 缺少外部事实/历史/媒体依据 → 调用原生 tool / MCP
        ↓
(6) Hermes 工具调用循环
    tool call → tool result → 继续模型推理 → 最终文本
        ↓
(7) Outbound safety gate
    - 静默 NO_REPLY
    - 拦截工具 trace、思考、JSON、框架状态、provider 错误
    - quiet 群物理静默
        ↓
(8) Bridge / OneBot 发送最终 QQ 消息
        ↓
(9) state.db、日志、审计样本记录真实结果
```

一个关键约束是：

> 工具调用可以发生在同一轮内部，但工具进度、等待、推理和错误详情都不应进入 QQ 群。群友只应看到最终自然回复，或什么也看不到。

## 四、工具调用闭环

### 1. 目标

模型不应把：

```text
“我去看一下”
“我去查查”
“我去整理”
```

当作聊天口头禅。

当模型作出查看、搜索、查历史、读文件、检查仓库等执行承诺时，正确链路应当是：

```text
识别信息缺口
→ 选择合适工具
→ 在当前 turn 调用工具
→ 获得结果
→ 只将最终结论写给群友
```

而不是：

```text
先向群发送“我去看”
→ 没有工具调用
→ 凭上下文继续发挥
```

### 2. 工具选择归属

| 需求 | 首选原生能力 |
|---|---|
| 查询网络事实 | Tavily MCP / Hermes web toolset |
| 查询 Hermes 旧会话 | `session_search` |
| 查询 QQ 最近群消息 | `qq_get_group_msg_history` |
| 查本地文件 | Hermes `file` toolset |
| 看图片或读图中文字 | Vision / OCR 工具 |
| 执行复杂可复用流程 | Skill |
| 定时复盘 | Cron + 独立 watchdog |

### 3. 工具健康状态

“工具 schema 被注入”不等于“工具当前可用”。

MCP 远端异常、认证问题、超时、连接 parking 都应由 Hermes MCP 生命周期处理。Profile 必须在工具失败时诚实降级：

```text
不能确认就说不能确认
不能把失败过程发群
不能用记忆伪造工具结果
```

## 五、渐进式披露与上下文控制

完整群聊系统不能把所有历史、每个用户档案、每条审计日志和全部工具教程常驻放进系统提示。

建议的读取层级：

```text
Layer 0：SOUL 核心
  身份、当前群隔离、最小接话原则、输出协议、工具真实性

Layer 1：当前群现场
  最近有效对话、当前发送者、当前群配置

Layer 2：按需资料
  历史检索、工具查证、媒体处理、当前群语气、当前用户摘要

Layer 3：审计和学习资料
  接话样本、watchdog、ITERATION_LOG、候选策略

Layer 4：原始证据
  state.db、原始 OneBot 消息、工具结果、日志
```

原则：

```text
普通聊天不主动读 Layer 2–4
当前问题需要什么，再取什么
详细经验先进入群级档案
跨群稳定规律才进入索引
极少数长期不变原则才进入 SOUL
```

## 六、用户画像与关系感知：计划状态

项目设计了用户画像与关系感知系统，但不应将其误解为“给群友打一个好感分，然后决定是否回复”。

推荐模型：

```text
用户身份（QQ 号主键）
→ 群内画像（兴趣、表达习惯、明确反馈）
→ 群内关系状态（熟悉度、互动温度、信任、边界敏感度）
→ 当前现场判断
```

其中：

- 关系状态只能调整称呼、语气、解释程度和互动细腻度；
- 关系状态不能直接决定是否回复；
- 关系状态不能赋予工具、管理或 owner 权限；
- 不同群的原始互动和关系状态必须隔离；
- 明确用户自述和行为推断必须分别记录置信度与证据；
- 负面反馈优先形成短期参与边界，而不是永久“讨厌某人”。

完整、可执行的阶段计划见：

[用户画像与关系感知迭代计划](plans/2026-09-01-keluomiao-user-profile-and-relationship-iteration.md)

## 七、当前代码的审查边界

`plugins/hermes_bridge.py` 保留了早期参考实现中的轻量消息分类和随机参与参数，用来演示 bridge 的短时调度边界。

这不应被理解为完整产品策略，更不应替代 Hermes Profile 的语义判断。完整系统的目标是：

```text
所有允许进入模型的群消息由模型结合现场决定是否参与
Bridge 只保留协议、安全、身份、并发、传输和最终输出边界
```

后续重构方向是进一步收缩 bridge 的行为判断，让它更纯粹地复用 Hermes 原生 Gateway 和 Agent workflow。所有改动都应先增加回归测试，再在独立 Profile / 单群 shadow 环境验证。

## 八、验证、审计与回滚

### 桥接层测试

当前仓库测试覆盖伪造 OneBot 事件与 mocked Hermes API 调用。测试不触碰真实 QQ、生产 Gateway、真实密钥或生产群聊数据。

```bash
python -m pytest -q
```

### 运行层审计

对真实部署，不应只看“服务是否存活”，而要区分：

```text
模型是否决定回复
模型是否调用工具
工具是否成功
最终是否 SEND OK
是否被 quiet / 安全层拦截
是否出现错误目标、低信息回复、内部泄露
```

### 灰度与回滚

新策略应采用：

```text
离线 holdout
→ 单群 shadow
→ 小范围灰度
→ 观察窗口
→ 通过、延长观察或回滚
```

每次修改 Profile、routing、模型、MCP 或 bridge 前都应保留配置/数据库备份。禁止通过删除真实聊天记录来“清理问题”。

## 九、隐私与开源边界

该仓库只发布可审查的桥接代码、脱敏配置模板、测试和设计文档。

绝不提交：

```text
真实 .env
API Key / Token
QQ 用户、群号、群成员名单
state.db
会话历史、群聊导出、日志
下载附件、媒体缓存
生产 Profile、用户画像、关系档案、Cron 输出
```

如果提交 Issue 或 PR，请使用脱敏复现样本，不要贴出真实聊天内容、密钥、账号或数据库。
